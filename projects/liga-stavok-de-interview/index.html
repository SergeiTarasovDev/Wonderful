    Фаза 1 · база

    SQL

    Трёхзначная логика, джойны, окна, планы. Диалекты: V = Vertica, CH = ClickHouse, MS = MSSQL.

    NULL — трёхзначная логика

    NULL — это «неизвестно», а не «пусто». Сравнение с NULL даёт NULL (UNKNOWN), а не TRUE/FALSE.

    sql
    -- НЕВЕРНО: всегда 0 строк
WHERE manager_id = NULL

-- ВЕРНО
WHERE manager_id IS NULL
    • Агрегаты игнорируют NULL, кроме COUNT(*). COUNT(col) ≠ COUNT(*); AVG(col) делит на число не-NULL.
    • NOT IN + NULL = пустой результат. Если подзапрос содержит NULL, NOT IN не вернёт ничего. Безопаснее NOT EXISTS.
    • NULL заражает арифметику и конкатенацию: 1 + NULL = NULL.
    sql
    COALESCE(a, b, 0)        -- первое не-NULL
NULLIF(x, 0)             -- x, если x <> 0, иначе NULL (защита от деления на 0)
x IS DISTINCT FROM y     -- NULL-safe сравнение (V, MS — через CASE)
    Ловушка ClickHouse

    NULL — отдельный тип Nullable(T), он дороже (битовая маска), по умолчанию колонки не Nullable. При join_use_nulls=0 (дефолт) LEFT JOIN заполняет пропуски дефолтными значениями (0, ''), а не NULL.

    JOIN — типы и три ловушки

    ТипЧто вернёт
    INNERТолько совпадения
    LEFTВсе левые + совпадения справа (или NULL/дефолт)
    FULL OUTERВсё с обеих сторон
    CROSSДекартово произведение
    SEMI / ANTIЕсть / нет совпадения — через EXISTS / NOT EXISTS

    Ловушка 1: фильтр не в том месте

    sql
    -- WHERE превращает LEFT JOIN в INNER
SELECT *
FROM orders o
LEFT JOIN payments p ON p.order_id = o.id
WHERE p.status = 'paid';          -- unmatched-строки отфильтрованы

-- Нужны и неоплаченные — условие в ON
LEFT JOIN payments p
  ON p.order_id = o.id AND p.status = 'paid'

    Ловушка 2: fan-out (размножение строк)

    JOIN с таблицей, где больше одной строки на ключ, увеличивает SUM/COUNT. Лечится предварительной агрегацией в CTE до джойна.

    Ловушка 3: анти-джойн

    sql
    -- Клиенты без заказов: NULL-безопасно
SELECT c.*
FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

    Оптимизация соединений

    • Sargability: WHERE date_trunc('day', ts) = ... не использует индекс/партиции. Пишите диапазон: ts >= '2026-01-01' AND ts < '2026-01-02'.
    • Неявные касты (varchar vs int) убивают hash/merge-join.
    • Фильтруйте до джойна — предикат-пушдаун.
    • Смотрите кардинальность: сильная ошибка оценки → плохой план.
    • CH: правая таблица грузится в память, порядок LEFT/RIGHT важен; в распределённом режиме — GLOBAL JOIN.

    Оконные функции

    Скелет: func(...) OVER (PARTITION BY ... ORDER BY ... frame).

    • Дефолтный frame при наличии ORDER BY — RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW, то есть накопительный итог. Без ORDER BY — весь партишн.
    • ROWS — по физическим строкам, RANGE — по значениям (дубликаты получают одинаковый итог).
    Для значений 1, 1, 2
    ФункцияРезультатКогда
    ROW_NUMBER()1, 2, 3Последняя запись на клиента
    RANK()1, 1, 3Пропуски после дублей
    DENSE_RANK()1, 1, 2Без пропусков
    sql
    -- Последний заказ на клиента
SELECT * FROM (
  SELECT o.*,
         ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY created_at DESC) AS rn
  FROM orders o
) t
WHERE rn = 1;

-- Прирост к предыдущему дню
SELECT dt, amount,
       amount - LAG(amount) OVER (ORDER BY dt) AS delta
FROM daily;

-- Доля в партишне
SELECT *, amount / SUM(amount) OVER (PARTITION BY month) AS share
FROM sales;
    Ловушка

    LAST_VALUE с дефолтным frame возвращает текущую строку. Нужен явный ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING. QUALIFY есть в V и CH, в MS — только через подзапрос/CTE.

    Планы запросов

    • EXPLAIN — оценка; EXPLAIN ANALYZE — фактические метрики (V; в CH — через send_logs_level и system.query_log).
    • Читаем: порядок соединений, тип join (hash / merge / nested loop), full scan вместо pruning, оценка vs факт по строкам.
    • V: проекции — «материализованный индекс»; проверить, использована ли проекция.
    • CH: read_rows, read_bytes, MemoryTracker; главный враг — чтение лишних партиций и колонок.
    • MS: actual execution plan, index scan vs seek, parameter sniffing.

    Глубже: что ещё спросить могут

    Подзапросы и CTE

    • CTE повышает читаемость, но в старых версиях MSSQL/Postgres может быть «optimization fence».
    • Коррелированный подзапрос vs EXISTS vs джойн — по плану.
    • Рекурсивный CTE — иерархии (партнёрские схемы, дерево агентов).

    Группировки и дедуп

    • GROUPING SETS, ROLLUP, CUBE — отчёты с итогами.
    • Дедуп: ROW_NUMBER() = 1, DISTINCT ON (PG), argMax (CH).
    • HAVING vs WHERE: фильтр по агрегату — только HAVING.

    Проверь себя

    Почему NOT IN с NULL может вернуть 0 строк?

    Потому что x <> NULL даёт UNKNOWN, и итоговый предикат никогда не становится TRUE. Спасает NOT EXISTS или фильтр IS NOT NULL в подзапросе.

    Чем WHERE после LEFT JOIN отличается от условия в ON?

    ON фильтрует до «дополнения» NULL-строками: unmatched остаются. WHERE применяется после и отбрасывает строки, где правая часть NULL, — LEFT JOIN фактически становится INNER.

    ROW_NUMBER vs RANK vs DENSE_RANK на 1,1,2

    1,2,3 / 1,1,3 / 1,1,2 соответственно.

    Что не так с WHERE DATE(ts) = '2026-01-01'?

    Функция на колонке ломает sargability: индекс и партиции не применяются, будет full scan. Переписать в диапазон по ts.

    Почему в ClickHouse LEFT JOIN вернул 0 вместо NULL?

    Дефолт join_use_nulls=0: пропуски заполняются дефолтными значениями типа. Включить join_use_nulls=1 или обрабатывать явно.

    Фаза 2 · база

    ClickHouse: база

    MergeTree-семейство, ORDER BY против PRIMARY KEY, партиционирование, жизненный цикл part'ов.

    Главная идея

    ClickHouse — колоночная OLAP-СУБД, оптимизированная под чтение. Она не «ещё один Postgres»: здесь нет настоящих транзакций и уникальных индексов, зато есть батчевые вставки, сжатие и чтение только нужных колонок.

    Семейство MergeTree

    Движки, которые надо знать наизусть
    ДвижокЧто делаетТипичный кейс
    MergeTreeБазовый: сортировка, партиции, индексы, TTLСырые события, логи
    ReplacingMergeTree(ver)Оставляет последнюю версию по sorting key при мержеCDC, upsert, дедуп
    SummingMergeTreeСуммирует числовые колонки по ключу при мержеПредагрегаты
    AggregatingMergeTreeХранит состояния агрегатных функций (-State), мержит ихMV-пайплайны, метрики
    CollapsingMergeTree(sign)Схлопывает пары +1/−1Удаление/изменение строк
    VersionedCollapsingMergeTree(sign, ver)То же, но корректно при неупорядоченных вставкахСтриминг без порядка
    Replicated*Префикс даёт репликацию через KeeperОтказоустойчивость
    DistributedНе хранит данные, фан-аут запросов по шардамШардированный кластер

    ORDER BY vs PRIMARY KEY — самое важное

    • ORDER BY — ключ сортировки. Определяет физический порядок строк в part'е и по нему строится разреженный первичный индекс.
    • PRIMARY KEY — необязателен, должен быть префиксом сортировочного ключа. Задаёт, по каким колонкам строится разреженный индекс. Если не указан — равен ORDER BY.
    • Разреженный индекс: одна запись на гранулу (index_granularity, по умолчанию 8192 строки). Поэтому индекс маленький и целиком в памяти.
    • Это не constraint: дубликаты и «нарушение порядка» не запрещены, просто данные физически отсортированы.
    • Правило выбора: в начало — колонки из WHERE, затем по возрастанию кардинальности. Но помните: ключ влияет и на скорость range-сканов.
    sql
    CREATE TABLE events (
  dt        Date,
  user_id   UInt64,
  event     LowCardinality(String),
  amount    Decimal(18, 2)
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(dt)
ORDER BY (event, dt, user_id)
SETTINGS index_granularity = 8192;

    Партиционирование и жизненный цикл данных

    • Partition — директория на диске. Внутри партиции лежат part'ы, по одному на вставку.
    • Фоновые мержи объединяют мелкие part'ы в крупные. Пока идёт мерж, старые и новые part'ы читаются вместе.
    • Слишком много партиций — плохо: ошибки «Too many parts», лишний overhead. Партиционируйте по месяцу/дню, а не по каждому значению.
    • Мониторинг: system.parts, system.part_log, system.merges.
    • OPTIMIZE TABLE ... FINAL — принудительный мерж, тяжёлая операция, не для продакшена «по расписанию».
    Классическая ошибка

    Вставлять по одной строке. Каждая вставка создаёт новый part, мержи не успевают — кластер деградирует. Вставляйте батчами (десятки тысяч строк) или используйте async inserts.

    Как CH читает запрос

    1. Partition pruning — отбрасываются партиции вне диапазона WHERE.
    2. Primary key pruning — по разреженному индексу отбрасываются гранулы.
    3. Чтение только нужных колонок — сила колоночного хранения; SELECT * убивает её.
    4. PREWHERE — сначала читаются колонки из предиката, фильтрация до чтения остальных; современный оптимизатор часто сам переносит условия.

    Проверь себя

    Чем PRIMARY KEY в ClickHouse отличается от обычной БД?

    Это не ограничение уникальности, а разреженный индекс: одна запись на гранулу, должен быть префиксом ORDER BY. Дубликаты разрешены.

    Что будет, если партиционировать по user_id?

    Тысячи/миллионы партиций → «Too many parts», катастрофический overhead на мержи и метаданные. Партиционируют по времени.

    Почему SELECT * в CH особенно плох?

    Колоночная БД читает только запрошенные колонки. * заставляет читать все, включая тяжёлые строковые, — кратный рост I/O.

    Зачем нужен PREWHERE?

    Позволяет отфильтровать строки, прочитав минимум колонок, до чтения остальных. Снижает объём I/O и памяти.

    Фаза 3 · продвинуто

    ClickHouse: продвинуто

    TTL, репликация и шардирование, мутации, async inserts, дедупликация, агрегаты и materialized views.

    TTL

    Удаление, перемещение на «холодный» диск/том или фоновая агрегация по возрасту данных.

    sql
    ALTER TABLE events
  MODIFY TTL dt + INTERVAL 90 DAY DELETE;

-- Переезд старых данных на другой диск/том
ALTER TABLE events
  MODIFY TTL dt + INTERVAL 30 DAY TO VOLUME 'cold';

-- Фоновая агрегация: свернуть детали в дневные суммы
ALTER TABLE events
  MODIFY TTL dt + INTERVAL 7 DAY
  GROUP BY dt, event
  SET amount = sum(amount);

    TTL выполняется на фоне при мержах. Ускорять удаление целыми партициями помогает ttl_only_drop_parts.

    Репликация и шардирование

    Репликация

    • ReplicatedMergeTree('/clickhouse/tables/{shard}/events', '{replica}').
    • Координация — ClickHouse Keeper (замена ZooKeeper).
    • Реплика — полная копия шарда; запись можно в любую, чтение — с любой.
    • Репликация асинхронная: возможна задержка; смотреть system.replicas.

    Шардирование

    • Данные делятся по sharding key между шардами.
    • Distributed(cluster, db, local_table, sharding_key) — витрина поверх локальных таблиц.
    • ON CLUSTER — DDL сразу на все узлы.
    • GLOBAL JOIN / GLOBAL IN — транслируют правую часть на все шарды; обычный join видит только локальные данные.
    Частая ошибка

    Сделать JOIN распределённой таблицы с распределённой таблицей без GLOBAL — получите неполные результаты, потому что каждый шард соединяет только свои строки.

    Мутации

    • ALTER TABLE ... UPDATE/DELETE — асинхронные мутации: перезаписывают затронутые part'ы целиком.
    • Тяжело и дорого. Для частых изменений лучше ReplacingMergeTree/CollapsingMergeTree или удаление целых партиций (ALTER TABLE ... DROP PARTITION).
    • mutations_sync = 2 — дождаться выполнения (для тестов, не для прода).
    • Лёгкие удаления: DELETE FROM ... WHERE — маска удалённых строк, дешевле мутации (зависит от версии).

    Асинхронные вставки

    sql
    SET async_insert = 1;
SET wait_for_async_insert = 1;          -- ждать подтверждения буферизации
SET async_insert_max_data_size = 10485760;
SET async_insert_busy_timeout_ms = 200;

    Сервер буферизует мелкие вставки и сам формирует крупные блоки → меньше part'ов, меньше «too many parts». wait_for_async_insert=1 даёт гарантию, что данные приняты в буфер (иначе можно потерять при падении).

    Дедупликация — два разных уровня

    1. На уровне вставок

    • insert_deduplicate=1 (по умолчанию для Replicated): повторная вставка того же блока игнорируется.
    • Спасает от ретраев, но не от логических дублей с другими данными.

    2. Логическая

    • ReplacingMergeTree(version) + FINAL или argMax при чтении.
    • Дедуп происходит в момент мержа, а не мгновенно.
    • OPTIMIZE ... DEDUPLICATE BY ... — принудительно.
    sql
    -- Актуальная версия без FINAL (дешевле на больших объёмах)
SELECT user_id, argMax(balance, updated_at) AS balance
FROM balances
GROUP BY user_id;

    Агрегатные функции

    • uniq() — приблизительный HLL-подсчёт, быстрый; uniqExact() — точный и дорогой; uniqCombined() — компромисс.
    • quantile(0.95)(x), quantiles(0.5, 0.9, 0.99)(x) — перцентили.
    • argMax(value, ts) / argMin — «последнее/первое значение по времени».
    • any(), anyLast(), groupArray(), groupUniqArray().
    • Комбинаторы: -If (условный), -Array (по массиву), -State/-Merge (состояния для MV).
    • AggregateFunction(uniq, UInt64) — тип состояния; SimpleAggregateFunction(sum, UInt64) — для sum/min/max/any.
    sql
    SELECT
  toStartOfHour(ts) AS hour,
  uniqExact(user_id) AS users,
  quantile(0.95)(latency_ms) AS p95,
  countIf(status = 'error') AS errors
FROM events
GROUP BY hour;

    Materialized views

    • MV — это триггер на INSERT в источнике: преобразует строки и пишет в целевую таблицу (или в таблицу через TO).
    • Старые данные MV не видит — нужен бэкфилл.
    • POPULATE заполняет при создании, но не атомарно и может пропустить вставки — в проде лучше ручной бэкфилл.
    • Канонический паттерн: источник → MV с GROUP BY и -State → AggregatingMergeTree → чтение через -Merge.
    • Refreshable MV (новые версии): REFRESH EVERY 1 HOUR — для батчевых витрин.
    sql
    CREATE TABLE events_hourly (
  hour      DateTime,
  event     LowCardinality(String),
  users     AggregateFunction(uniq, UInt64),
  amount    SimpleAggregateFunction(sum, Decimal(18,2))
)
ENGINE = AggregatingMergeTree
ORDER BY (hour, event);

CREATE MATERIALIZED VIEW mv_events_hourly TO events_hourly AS
SELECT
  toStartOfHour(ts) AS hour,
  event,
  uniqState(user_id) AS users,
  sum(amount)         AS amount
FROM events
GROUP BY hour, event;

-- Чтение:
SELECT hour, event, uniqMerge(users), sum(amount)
FROM events_hourly
GROUP BY hour, event;

    Проверь себя

    Почему FINAL может быть дорогим и что вместо него?

    FINAL заставляет схлопывать версии при чтении по всем затронутым part'ам. Альтернатива — argMax/GROUP BY, предварительный OPTIMIZE или проектирование так, чтобы дублей не было.

    Чем GLOBAL JOIN отличается от обычного в шардированном кластере?

    Обычный JOIN выполняется на каждом шарде только по локальным данным — результат неполный. GLOBAL транслирует правую таблицу на все шарды.

    Когда нужен AggregatingMergeTree, а когда SummingMergeTree?

    Summing — когда достаточно суммы простых числовых колонок. Aggregating — когда нужны состояния сложных агрегатов (uniq, quantile, avg), которые нельзя просто сложить.

    Материализованное представление увидит старые строки источника?

    Нет. MV реагирует только на новые вставки. Старые данные нужно залить в целевую таблицу отдельно (бэкфилл).

    Зачем wait_for_async_insert=1?

    Чтобы клиент получил подтверждение, что данные приняты в буфер сервера. С 0 можно «успешно» отправить и потерять при падении.

    ETL/ELT и КХД

    Слои, инкрементальная загрузка, идемпотентность, late-arriving data, SCD, Airflow, качество данных.

    Слои хранилища

    СлойЧто лежитПравило
    ODS / stagingСырые данные «как пришли», без бизнес-логикиНе терять историю, минимальные преобразования, легко перезалить

    Инкрементальная загрузка

    • High-water mark: храним последний загруженный ts/id в control-таблице, тянем только новее.
    • CDC: чтение лога изменений (Debezium, триггеры), а не опрос таблиц.
    • UPSERT/MERGE: Vertica MERGE, MSSQL MERGE, ClickHouse ReplacingMergeTree.
    • Partition overwrite: пересчитываем и заменяем целую партицию (идеально для больших пересчётов).

    Идемпотентность

    Повторный запуск пайплайна не должен менять результат. Это главный вопрос на собеседовании по ETL.

    • Ключ + версия, дедуп на записи.
    • DELETE/DROP PARTITION перед вставкой, затем загрузка.
    • Детерминированные трансформации: без now() и rand() в теле расчёта.
    • Транзакция или staging-таблица → атомарная подмена (EXCHANGE PARTITION / SWAP).
    • Идемпотентные ключи для внешних API.

    Late-arriving data

    • Lookback-окно: пересчитываем последние N дней, а не только «новые».
    • Watermark + allowed lateness: насколько опоздавшие события ещё принимаем.
    • Reprocessing/backfill: отдельный DAG/запуск за исторический период.
    • Для стриминга: оконные агрегаты и апдейты результатов по мере прихода событий.

    SCD — медленно меняющиеся измерения

    ТипПоведениеКогда
    SCD 0Не меняетсяКонстанты
    SCD 1Перезапись значенияИсправление ошибок, не нужна история

    -- 1) закрыть текущую строку, если атрибуты изменились
UPDATE dim_client
SET valid_to = :load_ts, is_current = 0
WHERE client_id = :id AND is_current = 1
  AND row_hash <> :new_hash;

-- 2) вставить новую версию
INSERT INTO dim_client
  (client_id, attr, row_hash, valid_from, valid_to, is_current)
VALUES (:id, :attr, :new_hash, :load_ts, '9999-12-31', 1);

    Что знать

    • Airflow 2 vs 3: asset/dataset-триггеры.

    Качество данных (DQ)

    • Полнота — доля NULL, пропущенные дни/партиции.
    • Уникальность — дубли по ключу.
    • Валидность — диапазоны, форматы, допустимые значения.
    • Согласованность — ссылочная целостность, сверки между слоями.
    • Свежесть — задержка данных, «последняя запись не старше N минут».
    • Объём — аномалии row count относительно предыдущих дней.

    Инструменты: dbt tests, Great Expectations, Soda Core, собственные проверки. Паттерн: проверка → карантинная таблица → алерт, а не молчаливое удаление строк.

    Проверь себя

    Как сделать пайплайн идемпотентным при загрузке в ClickHouse?

    Загружать в staging/временную партицию, затем атомарно подменять (EXCHANGE PARTITION или удаление и вставка партиции), либо использовать ReplacingMergeTree с версией и дедуп по ключу.

    Чем SCD2 отличается от SCD1 и когда что выбирать?

    SCD1 перезаписывает атрибут (история теряется), SCD2 добавляет версии строк с интервалами действия. SCD2 — когда нужна история изменений для отчётности.

    Как обрабатывать опоздавшие события?

    Lookback-окно, watermark + allowed lateness, периодический reprocessing затронутых партиций, бэкфилл DAG.

    Почему XCom нельзя использовать для больших данных?

    XCom хранится в метабазе Airflow и сериализуется — большие объёмы перегрузят БД и замедлят планировщик. Данные передают через storage, а в XCom — путь/идентификатор.

    Фаза 6 · домен

    Антифрод и беттинг

    Команда Риски — это антифрод. Понимание домена выделяет вас среди «просто DE».

    Домен беттинга в двух абзацах

    Букмекер принимает ставки на спортивные события. Линия и коэффициенты формирует трейдинг (в Лиге — 3000+ событий в день), маржа заложена в коэффициенты. Ставка проходит жизненный цикл: приём → расчёт (settlement) → выплата или возврат. Платежи (депозиты/выводы) — это «банк внутри компании».

    Для данных это означает: высокая частота событий, жёсткие требования к свежести, финансовая точность (Decimal, а не float) и регуляторные требования к хранению истории.

    Типы фрода

    • Мультиаккаунтинг — один человек под разными аккаунтами ради бонусов.
    • Bonus abuse — злоупотребление промо и фрибетами.
    • Арбитраж / вилки — ставки на все исходы ради безрисковой прибыли.
    • Account takeover — угон аккаунта.
    • Payment fraud — украденные карты, chargeback, отмывание.
    • Match-fixing / insider betting — договорные матчи, инсайд.
    • Affiliate fraud — накрутка партнёрских начислений.
    • Collusion — сговор групп аккаунтов.

    Типовая архитектура антифрода

    1. Сбор событий: ставки, депозиты, выводы, логины, устройства, IP — в Kafka.
    2. Обогащение и фичи: окна (1 мин / 1 час / 1 день), velocity, связки device/IP/карта, графовые признаки.
    3. Правила + ML-скоринг: rule engine даёт детерминированные срабатывания, модель — вероятность фрода.
    4. Решение: пропустить / лимитировать / заблокировать / отправить на ручной разбор.
    5. Case management: аналитик подтверждает или отклоняет — это источник меток.
    6. Обратная связь: метки → переобучение и бэктест; мониторинг дрифта.

    Особенности данных и ML-интеграции

    Данные

    • Сильный дисбаланс классов (фрода мало).
    • Запаздывающие метки: подтверждение приходит позже события.
    • Потоковые и батчевые источники нужно согласовать по времени.
    • Финансовые суммы — Decimal, никакого float.

    ML в проде

    • Онлайн-инференс с бюджетом задержки (< 100 мс) vs near-real-time vs batch.
    • Feature store, версионирование моделей и фич.
    • Shadow mode и A/B перед включением блокировок.
    • Бэктест на исторических данных с учётом задержки меток.
    • Метрики: precision/recall, стоимость FP vs FN, доля ручных разборов.

    Проверь себя

    Почему в антифроде нельзя оптимизировать только accuracy?

    Классы сильно несбалансированы: модель «всё легально» даст 99% accuracy и ноль пользы. Нужны precision/recall и стоимость ошибок.

    Как связать Kafka-партиционирование с качеством антифрода?

    Ключ по user_id гарантирует порядок событий одного пользователя в партиции — важно для корректного расчёта velocity-фич.

    Что делать с запаздывающими метками?

    Учитывать horizon метки в бэктесте, переобучать с задержкой, использовать прокси-метки (подтверждённые кейсы) и мониторить дрифт.
