Как устроен основной ETL: формирование витрин Datamart

Разбор операторов Airflow из dwh_operators.py и dwh_msbi_operators.py: от view в preparation до SCD-измерений, фактов, swap партиций и кубов MSBI. Материал рассчитан на инженера, который знает SQL и базово работал с Airflow.

Аудитория: DE / аналитик Код: plugins/dwh_operators_plugin Чтение: ~25 минут
Если совсем коротко
  1. Витрина — это цепочка из трёх объектов: view в preparation/prepared → промежуточная таблица P_* или etl_prepared.F_* → целевая таблица prepared.D_* / F_*.
  2. Измерения грузятся операторами SCD1/SCD2: генерация суррогатных _id, MERGE по _cd, обновление по hash_vl, для SCD2 — история через FROM_DT/TO_DT.
  3. Факты грузятся через init/reload: вставка в etl_prepared, проверка на пустоту, затем swap партиций в prepared и удаление по retention.
  4. Любой запуск пишет процесс в ETL_PROCESS_LOG, обновляет статистику Vertica и (для фактов) отправляет lineage в OpenMetadata.

Границы материала. Основной фокус — dwh_operators.py (7 операторов) и dwh_msbi_operators.py (GenerateViewForMSBI). Смежные темы — SQL Style Guide, правила создания DAG и DQ — даны ссылками, а не пересказом.

01

Общая картина: слои и объекты

Прежде чем читать код, зафиксируем главное: оператор не «пишет витрину» напрямую. Он управляет последовательностью объектов в трёх схемах Vertica. Понимание этой цепочки снимает 80% вопросов «почему упало» и «где смотреть результат».

Текстовая версия схемы
  1. Источники (SAP, 1C, API, файлы, public) попадают в preparation.
  2. Измерения: V_D_* → P_D_* → MERGE в prepared.D_*.
  3. Факты: prepared.V_F_* → etl_prepared.F_* → swap → prepared.F_*.
  4. Потребление: prepared.D_* / F_* → V_MSBI_* → MS SQL / куб MSBI.
preparation prepared etl_prepared BI / MSBI

Важное различие, которое часто путают. У измерений view лежит в preparation.V_D_*, а у фактов — в prepared.V_F_*. Это не ошибка: фактовый оператор создаёт view в той же схеме, где лежит целевая таблица (schema_name="prepared"), а измеренческий — в prepare_schema="preparation".

02

Жизненный цикл таски: от парсинга до записи в лог

Все операторы измерения и часть фактовых используют один и тот же каркас. Если понять эти пять шагов, дальше можно читать любой оператор как вариацию.

  1. Создание таски. Airflow передаёт параметры в __init__. Оператор сохраняет имена схем, префиксы и суффиксы, поднимает их в верхний регистр и запоминает sql-шаблон. Для SCD2 подменяет шаблон на tpl_prepared_reload_scd2_dim.sql.
  2. render_template_fields — сборка SQL. Перед execute Airflow вызывает этот метод. Оператор читает список полей целевой таблицы из Vertica (get_table_fields), определяет ключевые поля *_cd / *_id, собирает динамические куски: условие MERGE, списки полей для UPDATE/INSERT, подзапросы генерации id. Всё это кладётся в task.params, после чего Jinja рендерит .sql-шаблон.
  3. execute — подготовка и лог старта. Для SCD1 оператор сначала пересоздаёт view из файла репозитория. Затем begin_etl_process_log вставляет запись в ETL_PROCESS_LOG и возвращает pcs_id — номер процесса из последовательности.
  4. Выполнение блоков. Скрипт делится по маркеру /**BLOCK**/. Первый блок обычно TRUNCATE, затем INSERT ... SELECT из view, затем генерация id и MERGE. Каждый блок выполняется отдельным вызовом VerticaOperator.execute.
  5. Финализация. При успехе — ANALYZE_STATISTICS (если включено) и end_etl_process_log со статусом L и числом изменённых строк. При ошибке — error_etl_process_log со статусом E, кодом и описанием, затем AirflowException.
text ETL_PROCESS_LOG — жизненный цикл 
A  → старт:   INSERT … IA_STATUS_CD = 'A', IA_START_DTTM = NOW()
L  → успех:   UPDATE … IA_STATUS_CD = 'L', IA_FINISH_DTTM = NOW(), IA_ROW_CNT = count(*)
E  → ошибка:  UPDATE … IA_STATUS_CD = 'E', IA_ERROR_CD, IA_ERROR_DESC

Где чаще всего ломается новичок. Ошибка «Не удаётся определить ключевые поля» возникает не в execute, а в render_template_fields — ещё до первого SQL-блока. Это значит, что структура таблицы не совпала с ожиданием оператора: нет поля <dim>_cd / <dim>_id, либо для нестандартного измерения не передан key_fields.

04

Измерения: SCD1, SCD2 и создание структуры

Общий конвейер измерения

Независимо от типа измерения, логика одинаковая: view даёт плоский набор строк, промежуточная таблица P_* повторяет структуру целевой, а оператор решает, какие строки новые, какие изменились и какие исчезли.

Шаги шаблона tpl_prepared_reload_scd1_dim.sql
#БлокЧто делает
1TRUNCATE P_<DIM>Очищает промежуточную таблицу
2INSERT … SELECT * FROM V_<DIM>Кладёт актуальный срез источника
3Техническая запись _id = -1«Не определено»: _cd = '@', ACTV_IND = FALSE
4DELETE FROM ETL_DIM_ID WHERE tb = DIMЧистит генератор id по этому измерению
5INSERT INTO ETL_DIM_IDНовые _cd (которых нет в целевой) получают _id = ROW_NUMBER + max(_id)
6UPDATE P_ SET _id = …Проставляет сгенерированные id в промежуточную таблицу
7MERGE INTO D_ … USING P_Совпало и HASH_VL отличается — обновляет поля; не совпало — вставляет
8UPDATE D_ SET ACTV_IND = FALSEПомечает неактуальными записи, которых больше нет в источнике

Почему HASH_VL — это важно. Сравнение идёт не по всем полям, а по хешу неключевых атрибутов. Если в view не включить какой-то атрибут в HASH_VL, изменение этого атрибута не заметят. Если включить техническое поле, которое меняется каждый запуск, — MERGE будет обновлять всё подряд.

SCD1: только актуальная версия

Подходит для справочников, где история не нужна. При изменении атрибутов строка перезаписывается, а PCS_UDT_ID получает номер текущего процесса. Удалённые из источника записи не удаляются физически — у них выставляется ACTV_IND = FALSE и HASH_VL = HASH('UPDATED').

sql фрагмент MERGE (SCD1) 
MERGE INTO prepared.D_GN_CITY t
USING preparation.P_D_GN_CITY s
ON  nvl(s.CITY_CD, '@#$') = t.CITY_CD
WHEN MATCHED
 AND s.HASH_VL <> t.HASH_VL
THEN UPDATE SET
    CITY_VL      = s.CITY_VL,
    ACTV_IND     = s.ACTV_IND,
    HASH_VL      = s.HASH_VL,
    UDT_TMS      = s.UDT_TMS,
    PCS_UDT_ID   = {pcs_id}
WHEN NOT MATCHED THEN INSERT
    (CITY_ID, CITY_CD, CITY_VL, ACTV_IND, HASH_VL,
     ISRT_TMS, UDT_TMS, PCS_ISRT_ID, PCS_UDT_ID)
VALUES
    (s.CITY_ID, s.CITY_CD, s.CITY_VL, s.ACTV_IND, s.HASH_VL,
     s.ISRT_TMS, s.UDT_TMS, s.PCS_ISRT_ID, s.PCS_UDT_ID);

Списки полей и условие MERGE не пишутся в шаблоне руками — их собирает render_template_fields по фактическим колонкам таблицы.

SCD2: история изменений

SCD2 отличается тремя вещами: отбор новых строк идёт по (_cd, HASH_VL) среди актуальных (TO_DT = '9999-12-31'), при изменении старая запись получает TO_DT = now()::DATE, а после MERGE вставляется новая актуальная версия. Записи, исчезнувшие из источника, закрываются TO_DT = now()::DATE - 1.

Встроенная проверка на пустоту. В шаблоне SCD2 есть блок SELECT 1000000 / COUNT(1) FROM P_<DIM>. Если view вернул 0 строк, произойдёт деление на ноль и таска упадёт. Это защита от «успешной» загрузки пустого справочника, которая закрыла бы все записи.

Чем SCD2 отличается от SCD1
АспектSCD1SCD2

Изменениеперезапись полейзакрытие старой + вставка новой версии

ReloadDMDimOperator: legacy-оператор

Это более старый и более универсальный оператор. Он умеет иерархические измерения (поля *_lvl_cd / *_lvl_id), принимает key_fields для нестандартных ключей и генерирует id через последовательность измерения preparation.S_<DIM>. Для новых измерений его использовать не нужно: SCD1/SCD2 проще и предсказуемее. Держите его в голове, когда встретите в старых DAG.

CreateVerticaDMTDimensionSCD1Operator: создание структуры

Этот оператор не грузит данные — он создаёт объекты и проверяет, что view соответствует контракту. Его задача — не дать «кривому» справочнику попасть в prepared.

  1. Проверка длины имени. Название измерения — не больше 32 символов (ограничение поля tb в prp_seq_gen).
  2. Проверка набора и порядка полей. View обязан вернуть <dim>_id, <dim>_cd, <dim>_vl и технические поля в порядке из переменной dmt_dims_scd1_tech_clmns_names. Иначе — ошибка.
  3. Проверка форматов. _cd — текстовый, длина ≤ 30. _vl — текстовый, длина ≥ 25 (чтобы влезло «Не определено»).
  4. Проверка совместимости с бэкапом. Если таблица уже есть, создаётся временная таблица по новой структуре и в неё вставляются обязательные колонки из старой. Если вставка падает — структура несовместима.
  5. Бэкап. Существующая таблица копируется в <DIM>_bck_YYYYMMDD_HHMM. После пересоздания данные возвращаются, а HASH_VL сбрасывается в HASH('UPDATED'), чтобы следующий Reload обновил все атрибуты.
  6. Создание объектов. View, P_* без ограничений, целевая D_* с PRIMARY KEY (_id), UNIQUE (_cd), ORDER BY _id, UNSEGMENTED ALL NODES. При наличии etl_meta_dim_dct — запись в ETL_META_DIM.

create_VRT_D_GN_CITY >> update_VRT_D_GN_CITY

Пересоздание таблицы меняет id. Если структура изменилась и вы пересоздали измерение без восстановления из бэкапа, соответствие _id ↔ _cd может измениться. Это ломает факты, которые уже ссылаются на старые id. Поэтому оператор делает бэкап и возвращает данные, а DAG-практика — восстанавливать таблицу и перезапускать Reload.

05

Факты: init, reload и snapshot

Фактовые операторы устроены иначе, чем измеренческие: они не делают MERGE построчно, а заливают период в staging и меняют партиции местами. Это быстрее и атомарнее для больших объёмов.

Метаданные факта: ETL_META_FCT

Перед запуском оператор читает запись из prepared.ETL_META_FCT по fct_id = table_name. Если записи нет — таска падает.

Поля ETL_META_FCT, которые влияют на загрузку
ПолеЧто задаёт
fct_idИмя факта без префикса F_, например GN_PAYED_INVOICE
init_load_start_dtНижняя граница первичной загрузки
init_load_end_dtВерхняя граница первичной загрузки
reload_period_daysСколько дней назад перезаливать при reload. Если NULL — используется диапазон init
retention_period_daysСколько дней хранить. Влияет на delete_filter

Как считается период reload

text логика query_filter / delete_filter 
query_filter:
  reload_period_days IS NULL
    → init_load_start_dt / init_load_end_dt (или 1 = 1)
  reload_period_days IS NOT NULL
    → load_dt >= reload_date - reload_period_days
    → + load_dt <= reload_date   (если delete_last = True)

delete_filter:
  retention_period_days IS NOT NULL
    → load_dt <= reload_date - retention_period_days
    → + load_dt > reload_date    (если delete_last = True)
  retention_period_days IS NULL и delete_last = True
    → load_dt > reload_date
  иначе
    → 1 <> 1  (ничего не удаляем)

InitLoad: полная (пере)загрузка

  1. Читает DDL dependencies/sql/dmt/facts/<schema>/tables/<F_TABLE>.sql и Jinja-шаблон view .../views/<V_F_TABLE>.sql.
  2. Удаляет целевую таблицу и swap-копию, удаляет view.
  3. Создаёт целевую таблицу по DDL и swap-таблицу LIKE ... INCLUDING PROJECTIONS в etl_prepared.
  4. Создаёт view prepared.V_F_* и отправляет метаданные/план запроса (если включено).
  5. Вставляет INSERT INTO etl_prepared.F_* SELECT … FROM prepared.V_F_* с query_filter, добавляя isrt_tms, udt_tms, pcs_isrt_id, pcs_udt_id.
  6. Swap партиций из etl_prepared в prepared за диапазон дат.
  7. ANALYZE_STATISTICS, запись в ETL_PROCESS_LOG, lineage V_F_* → F_* в OpenMetadata.

Reload: инкрементальная перезагрузка

  1. TRUNCATE staging-таблицы etl_prepared.F_*.
  2. INSERT из view за период в staging (с профилированием запроса).
  3. Проверка на пустоту staging: если 0 строк — таска падает (защита от «успешной» пустой перезагрузки).
  4. SWAP_PARTITIONS_BETWEEN_TABLES для диапазона [reload_date - reload_period_days, 9999-12-31].
  5. DELETE по delete_filter — удаление устаревшего за пределами retention.
  6. ANALYZE_STATISTICS, лог, lineage (без удаления старого lineage).
python dmt_reload_fcts_ironman_sdk.py 
reload_VRT_F_GN_PAYED_INVOICE = ReloadVerticaDMTFactOperator(
    task_id="reload_VRT_F_GN_PAYED_INVOICE",
    vertica_conn_id="Vertica_airflow_datamart_writer",
    vertica_logging_conn_id="Vertica_airflow_datamart_logger_writer",
    reload_date=datetime.strftime(datetime.today(), "%Y-%m-%d"),
    table_name="GN_PAYED_INVOICE",
    schema_name="prepared",
    etl_schema_name="etl_prepared",
    fct_prefix="F_",
    bucket_name="analytics-ds-dev-airflow-artifacts",
)

InitLoadWithSnapshot: переинициализация без потери истории

Перед удалением таблицы оператор проверяет, есть ли в prepared.F_* данные. Если есть — делает COPY_TABLE в etl_prepared.F_*_SNAP_FOR_INIT. После пересоздания таблицы он вставляет пересечение колонок из snapshot, затем удаляет snapshot. Это спасает старые периоды, которых нет в текущем view.

Snapshot — это не «вечный бэкап». Он живёт только на время выполнения таски и удаляется в конце. Если нужна долгосрочная копия — делайте отдельный бэкап средствами Vertica/vbr, а не рассчитывайте на *_SNAP_FOR_INIT.

06

MSBI: как витрины попадают в кубы

MSBI не «читает» таблицы Vertica напрямую из куба. Цепочка такая: prepared.D_/F_ → V_MSBI_* (алиасы) → загрузка в MS SQL → пересчёт куба.

GenerateViewForMSBI

Оператор читает preparation.ETL_LABELS (соответствие table_name / column_name → column_alias), соединяет с v_catalog.columns и собирает SELECT column AS "alias". Результат — view prepared.V_MSBI_<table>. Если для таблицы нет ни одного лейбла, оператор падает: Не найдено записей для таблицы ….

python dmt_init_load_msbi_dims_view.py 
initload_V_MSBI_D_GN_BRANCH = GenerateViewForMSBI(
    task_id="initload_V_MSBI_D_GN_BRANCH",
    vertica_conn_id="Vertica_airflow_datamart_writer",
    table_name="D_GN_BRANCH",
)

Два типа MSBI DAG

msbi_reload_<cube>_facts / _dims

Загрузка в MS SQL

Используют MsSqlOperator и шаблон tpl_msbi_reload_table.sql. На выходе публикуют Dataset MSBI_<CUBE>_<TABLE>.

msbi_reload_<cube>_cube

Пересчёт куба

Запускается по Datasets от facts/dims. Выполняет tpl_msbi_recalc.sql и tpl_msbi_error_check.sql.

Куда смотреть, если куб не обновился. Сначала — на DAG загрузки facts/dims: он публикует Dataset. Затем — на cube-DAG: он должен быть запущен этим Dataset. Если Dataset не опубликовался, cube-DAG просто не стартует, и это не ошибка куба.

07

Разбор реальных DAG

dags/dmt/dmt_create_dims.py

Создание и обновление структуры измерений

Ручной DAG (schedule_interval=None), разбит на TaskGroup по доменам (create_gn_dims и т.д.). В каждой группе пары create_* → update_*. Запускается при изменении DDL view. Это «конструктор», а не ежедневная загрузка.

Что важно: create и update идут строго последовательно; сначала структура, потом данные.

dags/dmt/dmt_reload_dims_daily.py

Ежедневная загрузка измерений

Расписание из Variable dmt_dag_var_dct_1, max_active_runs=1, пул dmt_pool. Содержит TaskGroup по доменам и ReloadVerticaDMTDimensionSCD1Operator для каждого измерения. В конце — analyze_statistics.

Что важно: порядок тасок внутри группы задаётся вручную; если измерение зависит от другого, это должно быть явно в графе.

dags/ironman_sdk/dmt_reload_fcts_ironman_sdk.py

Перезагрузка фактов

Набор ReloadVerticaDMTFactOperator для фактов Ironman SDK. reload_date = сегодня, schema_name="prepared", etl_schema_name="etl_prepared", свой пул ironman_sdk_pool. Между фактами может быть явная зависимость (например, EMPLOYEE_HISTORY → SK_MOTIVATION).

Что важно: bucket_name и S3-коннектор нужны для выгрузки плана запроса; без них часть диагностики недоступна.

dags/msbi/ap/msbi_reload_ap_facts.py · msbi_reload_ap_cube.py

MSBI: факты и куб

Facts-DAG публикует Datasets MSBI_AP_DATA, MSBI_AP_SALDO и др. Cube-DAG запускается по ним и вызывает tpl_msbi_recalc.sql + tpl_msbi_error_check.sql через MsSqlOperator.

Что важно: в dev окружении расписание отключено (schedule=None), в prod — Dataset-триггеры.

Термины

SCD1
Slowly Changing Dimension type 1 — хранится только актуальная версия, изменения перезаписываются.
SCD2
Slowly Changing Dimension type 2 — хранится история версий через FROM_DT/TO_DT.
Суррогатный ключ
Искусственный _id, который генерирует ETL; не зависит от источника.
Swap партиций
SWAP_PARTITIONS_BETWEEN_TABLES — атомарная замена диапазона партиций между staging и target.
Lineage
Связь «источник → приёмник» в OpenMetadata; для фактов отправляется после успешной загрузки.
Staging
Промежуточная таблица в etl_prepared, куда пишется новый период перед swap.
